# 設計メモ

なぜこう作ったか。実装を読めば分かることは書かず、判断の理由だけ残す。

---

## 1. 外部発信は「禁止」ではなく「手段を渡さない」で止める

AI社員に `send_email` を渡して「勝手に送るな」とプロンプトで指示する設計にはしていない。
プロンプトは破られうるし、モデルが変わると挙動も変わる。

AI社員が持つのは `draft_email` / `draft_social_post` / `draft_calendar_event` /
`draft_listing_update` だけで、これらは**承認キューに行を作るだけ**の関数を呼ぶ。
実際に外部へ出るのは `src/lib/agents/dispatch.ts` の `executeApproval` で、
ここは人が承認したときにしか呼ばれない。

結果として「AI社員が誤送信する」という事故は、プロンプトの品質と無関係に起きない。
サイトで謳っている「AIが書いたものをそのまま出すことはありません」が、
運用ルールではなくコードの性質になっている。

**自動承認の抜け穴**: `tenant.settings.autoApprove` に入れたアクションだけは即実行される。
既定は空配列。口コミ返信のように量が多く事故の影響が小さいものを、
店舗ごとに開けていくための逃げ道として用意している。

---

## 2. 冪等性はスロット予約で担保する

ローカルの常駐ワーカーと Vercel Cron が同時に動いている状況を、
異常ではなく**通常の構成**として扱う。移行期には両方動くし、Cron はリトライもする。

`runs` テーブルの `slot_key`（`${jobId}@${分単位に丸めた時刻}`）に UNIQUE 制約を張り、
`INSERT ... ON CONFLICT DO NOTHING` の影響行数が 0 なら「他が既に取った」と判断して何もしない。

```
ワーカー ─┐
          ├─→ claimRunSlot("job_x@2026-08-14T09:30:00Z") ─→ 片方だけ true
Cron ─────┘
```

分単位で丸めているのは、cron の最小粒度が分だから。
これにより「同じメールの下書きが2通できる」が構造的に起きない。

承認の二重タップも同じ考え方で、`decideApproval` は
`WHERE status = 'pending'` 付きの UPDATE にしている。遷移できたときだけ実行に進む。

---

## 3. タイムゾーンは店舗のものを使う

サーバーが UTC でも、cron 式は**店舗のタイムゾーンの壁時計**で評価する。
`0 6 * * *` は「大阪の朝6時」であって、UTC の6時ではない。

`Intl.DateTimeFormat` の `formatToParts` で現地の時分・曜日を取り出して判定している
（`src/lib/scheduler/cron.ts`）。日報の「今日」の境界も同じ基準。
深夜1時の投稿が「昨日」に落ちない。

cron ライブラリを入れていないのは、必要なのが「今この分に該当するか」の判定だけで、
次回実行時刻の算出もジョブ常駐も要らないから。ワーカーも Cron も毎分呼ぶ形にしてある。

---

## 4. モックは「繋ぎ込みが終わるまで動かせない」を避けるためにある

`resolveConnectors(tenantId)` は認証情報の有無だけを見て、
揃っていなければモック実装を返す。判定はここ1箇所。

AI社員エンジンは `ConnectorBundle` インターフェースにしか依存していないので、
モックか実接続かを知らない。`.env` に鍵を入れた瞬間に本番接続へ切り替わり、
エンジン側のコードは1行も変わらない。

ただし**モックで動いていることは隠さない**。`connector.live` を UI の「接続状況」に出している。
繋がっているつもりで繋がっていない、が一番まずい。

---

## 5. 却下理由を次の実行に渡す

`runner.ts` は実行前に、そのAI社員が直近で却下された承認を5件まで引き、
却下理由を user プロンプトに載せる。

サイトの「直しが何度でも効く」を、口頭の運用ではなくデータの流れとして実装したもの。
店長が「金額に触れないでほしい」と一度書けば、次回以降の下書きに反映される。

## 6. DB は SQLite と Postgres の両対応。切り替えは環境変数1つ

`DATABASE_URL` があれば Postgres、無ければ SQLite。判定は `client.ts` の1行だけ。
これがそのままデプロイ先の選択になる（Render なら Postgres、VPS 1台なら SQLite）。

SQLite 側は Node 22 同梱の `node:sqlite` を使っている。ネイティブビルドが要らず
`npm install` だけで動くので、手元で詰まる箇所が減る。

**両対応のために払ったコスト**: `node:sqlite` は同期、`pg` は非同期なので、
リポジトリ層を全て非同期に揃えた。Server Component は async にできるので、
画面側の変更は `await` を足すだけで済んでいる。

方言差はドライバ層（`driver.ts` / `sqlite.ts` / `postgres.ts`）が吸収する。
実際に差があったのは2点だけだった:

- **プレースホルダ**: SQL は常に `?` で書き、Postgres 側で `$1, $2` に変換する
- **浮動小数の型名**: `REAL` と `DOUBLE PRECISION`

`INSERT ... ON CONFLICT DO NOTHING` と `ON CONFLICT (...) DO UPDATE SET ... = excluded....`
はどちらの方言でも同じ構文で通るので、`INSERT OR IGNORE` を使わず前者に統一した。

SQL は `repo.ts` に全て閉じてある。`types.ts` のドメイン型と repo の関数シグネチャは
DB 実装に依存していない。

**マルチテナントの約束**: 全テーブルが `tenant_id` を持ち、
一覧系の repo 関数は必ず `tenantId` を第一引数に取る。
テナントを跨いでデータが返る関数は `listAllEnabledJobs()`（スケジューラ用）だけで、
これは例外として明示してある。

## 7. プロンプトは Claude Opus 5 向けに書いている

`src/lib/agents/prompts.ts` で意図的にやっていること:

- **「必ず確認せよ」「二重チェックせよ」を書かない。** Opus 5 は指示がなくても自分の出力を
  検証する。書くと過剰検証になり、稼働時間とトークンだけが増える。
- **出力の長さを字数で縛らず、「何を落とすか」で指示する。** 字数上限は思考を圧迫する。
- **やらなかったことの説明を禁じている。** 既定では検討過程まで書きたがるが、
  スマホの画面でそれを読む時間はない。

`thinking: adaptive` + `effort: high` で動かし、`max_iterations: 24` で
1ジョブあたりのツール往復に上限を置いている（暴走時のコスト上限を兼ねる）。

---

## 8. UI は「朝の数分」に最適化している

店長がこの画面を開くのは移動中か開店前。設計上の優先順位は:

1. **スクロールせずに承認待ち件数が見える**（ホーム最上部の金色のカード）
2. **承認は1タップ**。却下だけ理由の入力を挟む（理由は次回に効くので価値がある）
3. **タップ領域は最低 48px**。厨房で片手で押す前提

Web フォントは読み込んでいない。iPhone の Hiragino Sans をそのまま使うほうが、
電波の弱い店内でも文字が即座に出る。

## 9. 費用を決めるのは起動回数なので、そこで削る

ホスティングは月1,000円以下に収まるが、モデルの実行はそうならない。
一次対応のジョブは30分ごとなので、それだけで月1,400回以上起動する。
そして問い合わせが常に来ているわけではないので、その大半は空振りになる。

`precheck.ts` は、モデルを呼ぶ前に「やることがあるか」だけを確かめる。
使うのはコネクタの読み取り（Gmail の一覧取得）だけで、これは無料。
新着が無ければ `skipped` として終え、モデルは1トークンも消費しない。

判断のポイントが3つある。

**判定に skipped を含めない。** 基準時刻は `getLastWorkedRunAt`（succeeded / failed のみ）
から取る。skipped を含めると基準が毎回動いてしまい、新着が来ていても
「前回スキップした時刻より古い」と判定してスキップし続ける。

**判定に失敗したら実行側に倒す。** トークン失効や Gmail の一時障害で受信箱が読めないとき、
スキップすると問い合わせを取りこぼす。1回分の費用を払うほうが安い。

**足切りしたことを隠さない。** `skipped` を `failed` と別の状態にしてあるので、
日報に「ほかに N 回は起動せず、費用が出ていません」と出せる。
削減率は店舗の問い合わせ量に依存するため、推定値ではなく実測を見せる。

種別を増やす場所は `shouldRunJob` の switch 1箇所。
「カレンダーに今日の予定が無ければ動かない」なども同じ形で足せる。

## 10. Instagram は「弾ける失敗は下書きの時点で弾く」

Instagram の Content Publishing API は制約が多く、投げてから怒られる要素が揃っている。
店長が承認ボタンを押した瞬間に失敗するのが一番まずいので、**同じ検証を2段階で持っている**。

1. **下書き時**（`tools.ts` の `draft_social_post`）— 画像の有無、枚数、登録済みURLか、
   キャプション長。ここで弾けば承認キューに載らず、AI社員はその場で作り直せる。
2. **公開時**（`instagram.ts` の `validate`）— 同じ検証に加えて https かどうか。
   コネクタ単体でも安全にしておく（他の経路から呼ばれても壊れない）。

重複しているのは意図的。1だけだと外部から `executeApproval` を叩かれたときに素通りし、
2だけだと店長の1タップを無駄にする。

**投稿枠はハードコードしない。** 1日の上限はアカウント種別や Meta 側の方針で変わるため、
`content_publishing_limit` から読んで判断する。読めなかった場合は投稿を試す
（枠の確認に失敗しただけで本題を落とさない）。

**API バージョンは環境変数で差し替える。** Meta は概ね四半期ごとに新版を出し、
旧版は約2年で廃止される。コードに埋めると2年ごとに必ず壊れる。

**予約投稿は黙って無視しない。** Content Publishing API に予約公開の仕組みは無い。
`scheduledFor` が指定されていたら、実行結果に「その時刻ではなく今公開した」と明記する。
指定を受け付けたように見せて実際は即時公開する、が一番たちが悪い。

### 写真ライブラリを足した理由

Instagram はテキストのみの投稿ができず、画像は Meta 側が取得する公開URLでなければならない。
つまり **AI社員は画像URLを自分で作れない**。ここを解かないと Instagram の自動化は成立しない。

`media_assets` に店舗の写真を登録し、`list_media` で選ばせる形にした。
下書きに未登録のURLが混ざっていたら `mediaUrlsAreRegistered` で弾く。
モデルがそれらしいURLを組み立ててしまう事故を、プロンプトではなくデータで止めている。

### 検証できていないこと

開発環境から `developers.facebook.com` と `graph.facebook.com` の双方に到達できなかったため
（egress ポリシーによる遮断。curl でも 403）、**公式ドキュメントとの突き合わせと実通信の
確認をしていない**。実装は既知の安定仕様に基づいており、`fetch` をスタブした24項目の
テストでリクエストの組み立て・2段フロー・カルーセル・エラー処理・上限チェックを確認している。

本番投入前に確認すべき点:
- 現行の Graph API バージョン（既定の `v25.0` が妥当か）
- 1日の投稿上限（コードは API から読むので影響は小さいが、挙動の確認は要る）
- Creator アカウントが公開に対応しているか（過去はビジネスのみだった）
- 必要なスコープ名（Facebook Login 経路か Instagram Login 経路かで異なる）

## 今後の判断が要る箇所

- **認証**: `src/app/approvals/actions.ts` の `currentActor()` が差し込み口。
  クライアント提供時はここをセッションから取る。同時に、全ページの
  `getDefaultTenant()` をセッション由来のテナント解決に置き換える。
- **Instagram の長期トークン更新**: 60日で失効する。失効前に自動更新するジョブか、
  失効を検知して承認画面に警告を出す仕組みが要る。現状は失効したら投稿が失敗するだけ。
- **X / MEO**: `src/lib/connectors/mock.ts` の2関数を実装に差し替える。
  インターフェースは確定済み。SNS の振り分けは `createRoutedSocialConnector` に足す。
- **写真の供給**: 現状 `media_assets` への登録は手動（シードのみ）。
  店舗が写真を追加する導線（アップロード画面か、共有ドライブとの同期）が要る。
- **費用の実測**: 事前チェックの削減率は店舗の問い合わせ量に依存する。1週間動かして
  日報のスキップ回数を見てから、cron の間隔や `effort` を調整する。
